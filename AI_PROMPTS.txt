    1. Python (Chosen) — Fastest to build/test, rich regex+subprocess libs, easy tests (pytest). Distribution via pip/uv. Tradeoff: needs interpreter installed.
    2. Go — Single static binary, what gitleaks/trufflehog use. Tradeoff: more boilerplate, slower to iterate on tests.
    3. Rust — Single binary, fast, safe. Tradeoff: steepest cost for regex-heavy tool.
    4. Node/TypeScript — Good ecosystem, but regex/perf and subprocess handling weaker fit for this.
Q2 [Detection] What secret-detection strategy should be core?
    1. Regex rules + entropy (Chosen) — Named regex patterns (AWS keys, private keys, tokens, passwords) + Shannon entropy as a signal for high-entropy strings. Best precision/recall balance, like gitleaks.
    2. Regex rules only — Simple, deterministic, low false positives, but misses unknown/novel secrets.
    3. Entropy only — Catches novel secrets but very high false-positive rate on normal code.
Q3 [Output] What output format(s)?
    1. Human text + JSON flag — Default readable table/list; --json for machine-readable results. Covers CLI use and CI integration.
    2. Human text only — Simplest, no schema to maintain.
    3. JSON only (Chosen) — Machine-first, less friendly for humans.
Q4 [Rules config] Should findings be committed to a secret-detection config schema, or hardcoded?
    1. Config file + built-in defaults (Chosen) — Ship default rule set; allow override/extension via a rules file. Extensible without code changes.
    2. Hardcoded rules only — Simplest, zero config surface, but editing rules means code edits.

1. Entropy only runs in credential context
The entropy pass checks CREDENTIAL_CONTEXT_RE first: it needs a credential-ish name followed by an = or :. That's behaving correctly: <component id="random"/> and <option value="random"/> don't flag, jobhunter_pass=hallelujah gets caught by the password rule instead of entropy, and api_key="..." is caught by the assignment rule before entropy is even needed. The explicit rules cover most of what entropy would find anyway, so letting them win makes sense.
If either XML example still shows up in a real run, check the rule field on the finding. Says entropy? Your running code doesn't match what's in the repo. Says something else? Then it's that rule's regex worth looking at.
2. secret_preview masks the wrong part
The regex detector masks the whole match, so for jobhunter_pass = "hallelujah" the preview shows a masked piece of the variable name instead of the password. Nothing leaks, but it's misleading.
Fix: add a named secret capture group to the assignment regexes that grabs just the value, and use m.groupdict().get("secret") or m.group(0) when building the finding. Rules without the group keep the current fallback. Minor priority output quality, not correctness.
3. AWS_ACCESS_KEY_ID doesn't match, but the README says it does
api-key-assignment only matches access_key when it's immediately followed by =, so _ID gets in the way and AWS_ACCESS_KEY_ID=... falls through to the aws-credential-var heuristic at medium. The README claims it's caught at high severity: that's wrong as written.
I'd add access_key_id as a proper keyword in the assignment rule and test it. Known credential names belong in explicit rules, not left to a heuristic.
